01 Why

一句话：让企业健身活动从“群里喊一喊”变成“可记录、可统计、可提醒”。

员工需要简单入口

每天用文本描述运动，系统解析后让员工确认，降低打卡成本。

管理员需要看得见

看板、排行榜、提醒任务和异常打卡审核，让活动能运营。

企业微信需要分场景

群机器人做公开通知，自建应用做个人提醒，避免公开点名。

02 What It Is

它不是“一个聊天机器人”，而是一套企业健身活动的闭环系统。

它要解决的事

  • 员工可以用一句话完成运动打卡。
  • AI 帮忙把自然语言整理成可统计数据。
  • 员工确认后，记录才进入榜单和统计。
  • 管理员能看打卡率、异常、提醒和榜单。
  • 企业微信负责把通知送到员工常用入口。

它暂时不做的事

  • 不做医疗诊断、疾病判断、药物建议。
  • 不把 AI 识别直接当作最终打卡事实。
  • MVP 不强制做图片识别和可穿戴设备同步。
  • 不在群里公开点名未打卡成员。
  • 不先做复杂积分商城和奖励兑换。
讲解口径：Open Fit 的主系统是 Web 工作台，企业微信是触达层，AI 是辅助层。
03 MVP Scope

MVP 先交付“能跑起来的活动”，不是一次性做完整运动 App。

模块 MVP 必做 后续增强
打卡 文本输入、识别、确认、修正、撤回、作废 图片识别、运动截图 OCR、批量导入
统计 有效打卡天数、累计运动时长、排行榜快照 团队赛、积分模型、奖励兑换
企业微信 群小贴士、周榜、OAuth 设计、个人提醒降级 多群绑定、复杂卡片、通讯录深度同步
AI 文本解析、健康咨询安全分类、拒答模板 多模态识别、个性化训练建议

02 Core Flow

主流程先抓住一个闭环：打卡、确认、统计、提醒。

初学者可以先记住这条线：用户输入不是最终事实，AI 只是助手，必须由用户确认后才进入排行榜。

员工输入文本描述运动内容
AI 解析提取类型、时长、距离
员工确认确认或修正识别结果
保存打卡写入有效记录
生成榜单按规则计算排名
提醒与推送个人提醒和群榜单
讲解重点：AI 输出不能直接污染统计，确认步骤是公平性和信任感的保护线。
06 Checkin Lifecycle

一条打卡记录不是“有或没有”，它会经历多个状态。

draft员工正在填写，尚未识别。
recognized系统已识别，等待确认。
submitted员工确认，有效计入统计。
corrected修正过，但仍可有效。
withdrawn员工撤回，不计入统计。
invalid管理员作废，必须写原因。
讲解重点：状态设计决定了公平性、可追溯性和排行榜可信度。

08 Tech Choices

技术选型按 MVP 落地优先：简单、可维护、后续能扩展。

前端

Vue 3 + Vite + TypeScript。适合企业内部工作台，开发快，结构清楚。

后端

Node.js + NestJS。模块化单体先跑起来，后续可按模块拆服务。

数据

PostgreSQL + Prisma。字段、枚举、索引和迁移都有清晰表达。

任务

Redis + BullMQ。处理小贴士、未打卡提醒、周榜推送和失败重试。

文件

本地磁盘存储。MVP 保存相对路径，通过后端鉴权访问。

部署

Docker Compose / 内网 VM。先降低运维复杂度。

06 WeCom

企业微信接入要分清“公开群消息”和“个人消息”。

群机器人

适合公开场景：每日小贴士、每周排行榜、群内 @ 咨询。

  • 不适合公开点名未打卡成员
  • 发送失败记录到提醒任务
  • webhook 密钥不能提交仓库
自建应用

适合个人场景：OAuth 登录、userid 映射、未打卡个人提醒。

  • 需要企业微信管理员权限
  • 权限不可用时降级到 Web 看板
  • access token 缓存在 Redis
讲解重点：群里只放适合大家看的信息，个人提醒不要变成公开压力。
13 WeCom Setup

企业微信接入可以按两条线讲：先群机器人，再自建应用。

步骤 群机器人 自建应用
1. 准备权限 群里添加机器人，拿到 webhook key 管理员创建应用，准备 corp id、agent id、secret
2. 系统配置 Web 配置密钥引用，绑定活动 配置可信域名、OAuth 回调、消息权限
3. 测试 发送测试小贴士到群 OAuth 登录并向指定 userid 发测试消息
4. 降级 失败进入重试和管理员查看 个人提醒不可用时转为 manual 任务
14 API Map

前端每个动作都要能找到后端接口和数据变化。

POST /api/checkins/recognize文本识别，创建待确认打卡和识别结果。
POST /api/checkins/:id/submit员工确认，打卡进入有效统计。
GET /api/leaderboards/current读取当前排行榜快照和规则说明。
POST /api/admin/checkins/:id/invalidate管理员作废异常记录，并写审计日志。
GET /api/admin/reminders查看待发送、失败、manual 提醒任务。
POST /api/admin/wecom/test-message测试企业微信配置是否可用。
07 Data Model

数据表先记住五组：人、活动、打卡、榜单、提醒。

表 用来做什么 新手理解
members 员工、企业微信 userid、角色 谁在参加活动
activities 活动周期、规则、提醒时间 这次活动怎么玩
checkins 打卡内容、状态、修正与作废 每个人每天交了什么
leaderboard_entries 排名、得分、打卡天数、运动时长 榜单上怎么排
reminder_tasks 未打卡提醒、发送状态、失败原因 谁还需要提醒
16 Data Relationships

数据表关系可以这样理解：活动把人、打卡、榜单和提醒串起来。

members
员工身份、部门、角色、wecom_userid。
activities
活动周期、规则、提醒时间。
checkins
每天的打卡状态和最终统计字段。
leaderboards
按周期生成快照和排名条目。
reminders
未打卡提醒、失败、manual、重试。
AI 结果单独存

recognition_results 保存模型输出、置信度和提示，方便解释和追踪。

操作必须留痕

audit_logs 记录管理员作废、配置修改和敏感操作。

08 Safety

AI 教练可以给建议，但不能像医生一样诊断。

normal

普通运动、饮食、健康知识，可以给低风险建议。

caution

涉及个人身体状况时要保守回答，并说明不是医疗建议。

escalate

胸痛、晕厥、急性损伤、药物、孕产、极端减重，必须建议专业帮助。

讲解重点：健康安全不是文案问题，是系统必须内置的分类和拒答流程。
18 Local Storage

文件采用本地存储，但不能把上传目录直接暴露出去。

存储约定
  • 根目录由 LOCAL_STORAGE_ROOT 指定。
  • 按组织、活动、日期分层保存。
  • 数据库只保存相对路径，不保存绝对磁盘路径。
访问约定
  • 必须通过后端鉴权路由读取。
  • 删除先标记状态，再由清理任务删磁盘文件。
  • MVP 图片入口可保留，但不作为强制上线能力。
09 Build Plan

实施顺序：先跑通闭环，再接企业微信，再增强体验。

阶段 1
基础工程
Vue 3 工作台、Node.js/NestJS API、PostgreSQL、Redis、Prisma、本地文件目录。
阶段 2
打卡闭环
成员、活动、文本打卡、AI/规则解析、用户确认、修正撤回。
阶段 3
榜单与提醒
排行榜快照、未打卡提醒任务、管理员看板、失败重试。
阶段 4
企业微信接入
群机器人小贴士和周榜，自建应用 OAuth、userid、个人提醒。
阶段 5
AI 安全与增强
健康咨询分类、拒答模板、免责声明、图片识别扩展。
20 Acceptance

验收时不要只问“页面有没有”，要问闭环是否真的成立。

员工能不能从文本输入、AI 识别、手动修正到确认提交，完整完成一次有效打卡？
排行榜是否只统计有效记录，并能解释排序规则和更新时间？
群机器人能否发送小贴士和周榜，自建应用不可用时是否能降级为 manual 提醒？
管理员作废、重试、配置测试等关键操作是否有审计记录？
AI 对胸痛、晕厥、急性损伤、药物、孕产、极端减重等高风险问题是否拒绝诊断？
10 What To Review

和同事沟通时，最后确认这五件事。

技术栈

Vue 3、Node.js/NestJS、PostgreSQL、Redis/BullMQ、Prisma、本地存储。

企业微信权限

是否能用自建应用、OAuth、userid 和应用消息。

排行榜规则

有效打卡天数、累计时长、平局规则、补卡是否计入。

隐私策略

图片本地存储、访问权限、删除策略、咨询日志保留。

AI 安全

高风险问题拒答，普通问题才给低风险建议。

验证方式

自动测试、企业微信测试消息、页面隐私检查、知识库回写。
