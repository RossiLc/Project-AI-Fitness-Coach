# 决策记录

## DR-001：项目文档默认使用中文

- 状态：已接受。
- 决策：项目自写文档、OpenSpec 产物、知识库和说明统一使用中文。
- 原因：降低团队协作和交接成本。

## DR-002：使用 OpenSpec + spec-driven-superpowers

- 状态：已接受。
- 决策：使用 OpenSpec 管理变更，用 spec-driven-superpowers 强化门禁、计划和验证。
- 原因：项目涉及企业微信、AI、健康建议、隐私和 Web 平台，需要更强流程约束。

## DR-003：建立长期知识库

- 状态：已接受。
- 决策：使用 `docs/知识库/` 维护长期项目知识。
- 原因：OpenSpec change 适合记录单次需求，长期知识需要独立沉淀。

## DR-004：Superpowers 运行时优先

- 状态：已接受。
- 决策：当 Agent 能看到 Superpowers 技能时，必须优先调用真实技能；否则才 fallback。
- 原因：这更符合标准 spec-superflow 的推荐用法，OpenSpec 负责规格生命周期，Superpowers 负责执行纪律和门禁。

## DR-005：只保留项目级可加载技能，不保留完整源码快照

- 状态：已接受。
- 决策：不保留 `.codex/vendor/superpowers` 这类完整上游源码快照；项目只保留 Codex 实际需要加载的 `.codex/skills/`。
- 原因：减少第三方源码噪音，避免把上游工程误认为 Open Fit 业务源码。

## DR-006：Superpowers 上游运行资产保持完整

- 状态：已接受。
- 决策：`.codex/skills/` 中来自 Superpowers 上游的技能文件、脚本、参考文档、prompt 和示例文件尽量保持原貌，不为了中文化或表面整洁而裁剪。
- 原因：Superpowers 的约束能力来自技能说明、脚本、参考材料和流程门禁的组合。过度删除会让流程退化成普通提示词。

## DR-007：方案级 OpenSpec 门禁

- 状态：已接受。
- 决策：对从 0 到 1 产品、跨端平台、企业集成、架构选型或多模块系统，OpenSpec 必须按 `solution-architecture` 级别产出方案，强制覆盖技术选型、前端工作台、后端服务、企业集成、AI 服务、数据模型、流程架构、部署运维、安全隐私和验证矩阵。
- 原因：通用 OpenSpec 模板容易产出方向性文档，无法支撑复杂平台落地。方案级门禁把“可落地深度”从 Agent 自觉变为产物结构约束。

## DR-008：Open Fit MVP 推荐技术栈

- 状态：已接受。
- 决策：MVP 方案采用 Vue 3、Vite、TypeScript、Node.js、NestJS、PostgreSQL、Redis/BullMQ、Prisma、本地磁盘存储和 Docker Compose。
- 原因：Vue 适合快速构建企业内部工作台；Node.js/NestJS 支持模块化后端、异步任务、企业微信集成和 AI 适配；本地磁盘存储满足 MVP 文件管理要求，后续多实例部署时可迁移到对象存储。

## DR-009：企业微信智能机器人仅使用长连接

- 状态：已接受。
- 决策：Open Fit 智能机器人入站只采用企业微信官方 SDK 长连接方式，分别为打卡助手和 AI 教练配置 `Bot ID + Secret`；不保留 URL 回调 fallback。
- 原因：长连接由 SDK 处理认证、心跳和重连，联调时只需替换机器人凭证；双机器人职责通过连接配置注入，能降低打卡误入库风险，并复用同一业务处理服务。删除 URL 回调入口可以减少配置分支和生产暴露面。
