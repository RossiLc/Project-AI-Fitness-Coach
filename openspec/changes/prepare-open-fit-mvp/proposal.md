# Proposal

## Motivation

`analyze-open-fit-requirements` 已经完成 Open Fit 的需求分析，但尚不足以指导工程落地。Open Fit 不是单点功能，而是一个包含企业微信接入、Web 工作台、AI 识别与问答、运动打卡、排行榜、提醒任务、权限隐私和数据治理的跨端平台。

如果没有方案级设计，后续实现会在技术栈、企业微信身份映射、前后端职责、数据表、调度任务、AI 安全边界和页面流程上反复返工。本变更将 `prepare-open-fit-mvp` 升级为可落地的 MVP 方案设计，为后续编码型变更提供工程蓝图。

## Scope

本次做：

- 给出 Open Fit MVP 的推荐技术栈、备选方案和取舍理由。
- 设计系统架构、模块边界、部署拓扑和端到端数据流。
- 设计企业微信群机器人、自建应用、OAuth 登录、userid 映射、消息发送和降级路径。
- 设计 Web 工作台的信息架构、员工端、管理员端和企业配置端页面。
- 设计后端服务模块、API 边界、调度任务、权限控制和错误处理。
- 设计 AI 文本解析、图片识别扩展、健康咨询、安全分类和用户确认链路。
- 设计 PostgreSQL 数据表、关键字段、索引、状态枚举和数据保留策略。
- 设计打卡、AI 识别确认、排行榜、未打卡提醒、健康咨询和管理员修正流程。
- 形成方案级任务、验证矩阵、实现门禁和知识库回写要求。

本次不做：

- 不直接实现业务代码、数据库迁移、Web 页面或企业微信生产联调。
- 不提交真实企业微信凭证、access token、员工数据或生产 webhook。
- 不把图片识别、复杂团队赛、奖励体系、积分商城作为 MVP 必交付。
- 不提供医疗诊断、治疗、处方、药物调整、康复处方或疾病管理结论。

## Change Level

solution-architecture

本变更属于从 0 到 1 产品平台的方案级变更，必须覆盖技术选型、前端、后端、集成、数据模型、业务流程、部署运维、安全隐私和验证矩阵。

## Success Criteria

- `design.md` 能让后续实现者明确使用什么技术栈、如何拆前后端模块、如何设计表、如何接企业微信、如何处理 AI 和调度任务。
- Web 工作台覆盖员工打卡、个人数据、排行榜、管理员看板、活动配置、打卡审核、提醒任务和企业微信配置。
- 后端服务边界覆盖身份、活动、打卡、AI 识别、排行榜、提醒、企业微信、健康咨询、审计和配置。
- 数据模型包含 MVP 所需核心表、字段、状态、索引、关系和删除/保留策略。
- 企业微信接入方案覆盖群机器人、自建应用消息、OAuth 登录、成员同步、消息回调和权限不可用时的降级。
- 验证矩阵覆盖文本打卡、图片扩展、AI 安全、排行榜、提醒、企业微信消息、权限、隐私和知识库回写。
- 后续可基于 `tasks.md` 和 `plan.md` 直接创建实现型变更或进入 apply 阶段。

## Required Solution Coverage

- 技术选型：前端、后端、数据库、缓存/队列、AI 服务、文件存储、部署方式。
- 前端：角色、导航、页面、组件、状态、空态、错误态、移动端适配。
- 后端：模块边界、REST API、异步任务、权限、配置、错误处理。
- 企业微信：群机器人、自建应用、OAuth、userid 映射、消息格式、降级策略。
- AI：文本解析、图片识别扩展、健康咨询、安全分类、人工确认、日志。
- 数据模型：表结构、字段、枚举、索引、外键关系、软删除和审计。
- 流程架构：打卡、识别确认、排行榜、提醒、咨询、管理员修正。
- 部署运维：环境变量、密钥、日志、监控、备份、任务重试、回滚。
- 验证矩阵：每个能力的自动/人工验证方式、通过标准和证据位置。

## Out of Scope

- 生产级高可用微服务拆分。
- 多租户商业化 SaaS 计费与租户隔离。
- 可穿戴设备接入、第三方运动平台 OAuth 和实时运动数据同步。
- 医疗级健康评估、疾病风险评分和专业康复计划。
- 完整视觉稿或高保真原型；本变更只定义工作台信息架构和页面级设计要求。

## Open Questions

- 企业微信管理员是否允许创建自建应用、读取成员 userid、配置可信域名和发送应用消息？
- MVP 是否必须使用企业微信 OAuth 登录，还是可先使用企业内部 SSO / 临时账号再迁移？
- 图片数据是否允许保存原图；若保存，保留期限、访问角色、删除策略是什么？
- 排行榜主指标最终采用“有效打卡天数 + 累计运动时长”，还是积分模型？
- 企业是否需要健康咨询日志人工审核；如需要，谁能查看、保留多久？
